1.1 작품 주제 선정 배경

1990년대 출시된 휴대용 전자 펫 장난감 '다마고치(Tamagotchi)'는 가상의 생물을 돌보는 육성 게임으로 전 세계적으로 큰 인기를 끌었다. 이 프로젝트는 해당 콘셉트를 현대적인 터미널 기반 RPG 형식으로 재해석하여, 캐릭터를 직접 키우고 훈련시키며 전투에 참여하는 복합 장르 게임을 구현하는 것을 목표로 한다.

현대 게임 시장에서 단순한 캐주얼 육성 게임은 여전히 많은 수요가 있으며, C++ 언어의 객체지향 프로그래밍(OOP) 원리를 실제 게임 개발에 적용해보는 학습 목적도 겸한다.

주제 선정 이유:
캐릭터 육성, 전투, 훈련, 장비 등 다양한 기능을 모듈 단위로 나눠 OOP 설계를 자연스럽게 실습할 수 있다.
터미널 환경에서 마우스·키보드 입력, ANSI 색상, 커서 제어 등 저수준 I/O 기술을 습득할 수 있다.
게임이라는 친숙한 도메인으로 팀 협업의 동기를 부여할 수 있다.
설계한 로직을 시각적으로 보여주기 효과적인 '게임' 카테고리를 주제로 선정하였다.


1.2 벤치마킹

반다이 다마고치 (https://tamagotchi.fandom.com/wiki/Care)
기본 육성 콘셉트를 참고하였다. 배고픔·행복도·청결도·건강 등 생존에 직결된 핵심 수치를 실시간으로 관리하는 다마고치 특유의 육성 로직을 프로젝트의 기초 시스템으로 채택하였다.

디지몬 월드 (https://digimon_world_psx.fandom.com/wiki/Evolving-Your-Digimon)
훈련 시스템을 참고하였다. 마을 내 훈련 시설에서 공격력·방어력·지능 등 세부 스탯을 직접 선택하여 올리는 '목적형 육성' 방식을 채택하였다. 또한 필드 내 야생 몬스터와 보스를 격파하며 점진적으로 다음 지역을 해금해 나가는 '스테이지 단계별 클리어' 형식을 도입하였다.

언더테일 (https://www.gamedeveloper.com/design/game_design_deep_dive_i_undertale_i_s_action_based_rpg_battles)
터미널 스타일 UI, 텍스트 기반 전투 시스템을 참고하였다. 전투 화면의 ASCII 아트 활용 방식과 전략적 선택지 제공 방식에 영향을 받았다.

2.1 전체 아키텍처 (MVC 패턴)

본 프로젝트는 MVC(Model-View-Controller) 패턴을 기반으로 설계되었다.

Model (데이터 계층):
Character - 플레이어 데이터 (육성 스탯, 전투 스탯, 장비, 아이템)
Monster   - 몬스터 데이터 (스테이지별 HP, 공격력, 회피율, ASCII 아트)
Equipment - 검/갑옷 티어 테이블 (정적 데이터)
Item      - 아이템 테이블 (정적 데이터)

View (출력 계층):
Renderer  - ANSI 색상, ASCII 아트 렌더링, 화면 레이아웃 유틸리티 (정적 클래스)

Controller (제어 계층):
GameEngine    - 게임 루프, 화면 전환, 엔딩 조건 판정
InputHandler  - termios 기반 raw mode, xterm 마우스 프로토콜 파싱
Screen (추상) - 모든 화면의 공통 인터페이스
각 Screen 서브클래스 - 화면별 렌더링 및 입력 처리

이 구조를 통해 화면 추가 시 Screen 서브클래스 하나만 작성하면 되는 확장성을 확보하였다.

2.3 클래스 다이어그램 및 상속 구조

추상 기반 클래스 Screen은 두 개의 순수 가상 함수를 선언한다.

class Screen {
public:
virtual ~Screen() = default;
virtual void render(const Character& player) = 0;
virtual void handleInput(GameEngine& engine, Character& player, const InputEvent& event) = 0;
virtual bool needsRedraw() const { return false; }
};

Screen을 상속하는 8개의 구체 클래스:
MainScreen        - 메인 허브 화면
RaisingScreen     - 육성 화면 (먹이/목욕/놀기/치료)
BattleScreen      - 전투 화면 (스테이지 선택 → 가위바위보)
TrainingScreen    - 훈련 선택 허브
EquipmentScreen   - 장비/아이템 상점 화면
PunchingBagScreen - 샌드백 치기 미니게임
RunningScreen     - 달리기 미니게임
ReactionScreen    - 반응속도 측정 미니게임
EndingScreen      - 엔딩 화면

상속 계층도:
Screen (추상 클래스)
├── MainScreen
├── RaisingScreen
├── BattleScreen
├── TrainingScreen
│   ├── PunchingBagScreen
│   ├── RunningScreen
│   └── ReactionScreen
├── EquipmentScreen
└── EndingScreen


2.4 사용자 경험(UX) 흐름

게임 시작
↓
MainScreen (메인 허브: 육성/전투/장비/훈련 선택)
├── [육성] → RaisingScreen (밥주기/목욕/놀아주기/치료)
├── [전투] → BattleScreen → 스테이지 선택 → 가위바위보 전투 → 승리/패배
├── [장비] → EquipmentScreen → 검 강화/갑옷 강화/아이템 구매
└── [훈련] → TrainingScreen
├── [샌드백치기] → PunchingBagScreen (공격력 +8)
├── [달리기]    → RunningScreen (최대HP +20)
└── [반응속도]  → ReactionScreen (민첩 +1~6)

스탯 0 도달 시 → EndingScreen (배고픔/행복/청결/건강에 따라 4종)
5스테이지 클리어 시 → EndingScreen (용사 엔딩)


2.5 화면 구성 및 UI 설계

터미널 화면은 총 161컬럼 × 44행 고정 레이아웃을 사용한다.

상단 메뉴 바 (2행):
캐릭터 이름 | 날짜 | 배고픔[바] | 행복[바] | 청결[바] | 건강[바] | 돈 | 스탯(공격/체력/민첩)

콘텐츠 영역 (36행):
화면별 ASCII 아트 + 정보 패널 3열 구성

하단 버튼 바 (2행):
기능별 버튼 (마우스 클릭으로 조작)

화면별 주요 UI:
MainScreen       - 캐릭터 ASCII 아트(구치파치) + 4개 메뉴 버튼
RaisingScreen    - 캐릭터 아트 + 애니메이션(먹기/목욕/놀기/치료) + 5개 버튼
BattleScreen     - 스테이지 선택(좌), 몬스터 아트(중), 몬스터 정보(우) / 전투 시 HP바 + 가위바위보 손
TrainingScreen   - 캐릭터 아트 + 3개 훈련 선택 버튼
PunchingBagScreen- 캐릭터(좌) | 진행바/카운트(중) | 샌드백(우)
RunningScreen    - 캐릭터가 좌→우로 이동하며 결승선 도달
ReactionScreen   - 캐릭터(좌) | 과녁 + 반응시간(우), 색상으로 상태 표시
EquipmentScreen  - 검/갑옷 아트 + 강화 정보 + 아이템 인벤토리

3.1 게임 엔진 및 입출력 시스템

담당: 조광일

[게임 엔진 - GameEngine]

GameEngine은 게임의 핵심 루프를 담당한다.
멤버 변수: bool running, Character player, unique_ptr<Screen> currentScreen, InputHandler inputHandler

게임 루프 구조 (GameEngine::run):
while (running) {
InputEvent event = inputHandler.pollEvent();  // 논블로킹 입력 대기
currentScreen->handleInput(*this, player, event);  // 입력 처리
if (player.isEndingCondition()) { ... }  // 엔딩 조건 판정
currentScreen->render(player);  // 화면 렌더링
}

화면 전환은 changeScreen(std::make_unique<BattleScreen>()) 한 줄로 처리된다.
이것이 다형성의 핵심으로, if-else 분기 없이 Screen* 타입으로 어떤 화면이든 동일하게 처리한다.

엔딩 조건 판정:
배고픔 0 → 굶주림 엔딩 (STARVE)
행복도 0 → 도망 엔딩 (RUNAWAY)
청결도 0 → 쓰레기 엔딩 (TRASH)
건강 0   → 병원 엔딩 (HOSPITAL)
5스테이지 클리어 → 용사 엔딩 (HERO)

초기화 시 stdout을 완전 버퍼링(65536바이트)으로 설정하여, 프레임 전체를 한 번에 출력함으로써 화면 깜빡임을 방지한다.

[입력 시스템 - InputHandler]

termios를 활용한 raw mode 입력 처리:
원래 터미널은 Enter 입력 후 전달되는 정규 모드(canonical mode)로 동작한다.
이를 raw mode로 변경하여 키 입력 즉시 처리한다.
게임 종료 시 원래 터미널 설정으로 복원하는 RAII 구조를 적용하였다.
Ctrl+C 등 비정상 종료 시에도 복원되도록 정적 시그널 핸들러를 등록하였다.

xterm 마우스 프로토콜 파싱:
터미널의 마우스 클릭 정보는 ESC 코드로 시작하는 암호 같은 바이트 시퀀스로 전달된다.
이를 단계별로 해석하는 파서를 직접 구현하여, 클릭한 버튼의 좌표와 버튼 번호를 추출한다.
추출된 좌표를 기반으로 어느 버튼이 눌렸는지 계산하는 방식으로 모든 화면의 입력을 처리한다.

pollEvent()는 100ms 타임아웃을 가진 논블로킹 방식으로 동작하여,
입력이 없는 동안에도 타이머 기반 애니메이션(RaisingScreen, ReactionScreen 등)이 정상 동작한다.


3.2 육성 시스템

담당: 정주연

[캐릭터 모델 - Character]

캐릭터는 두 종류의 스탯을 보유한다.

육성 스탯 (0~100, clampStats()로 범위 유지):
hunger      - 배고픔 (초기값 70)
happiness   - 행복도 (초기값 70)
cleanliness - 청결도 (초기값 70)
health      - 건강   (초기값 70)

전투 스탯:
attack  - 기본 공격력 (초기값 20)
hp      - 현재 HP     (초기값 100)
maxHp   - 최대 HP     (초기값 100)
agility - 민첩도 / 회피율 (초기값 5%)

초기 소지금: 500원

[육성 액션 - RaisingScreen]

밥주기 (feed):
hunger +20, happiness +5
캐릭터 먹는 애니메이션 1.2초 재생

목욕하기 (bath):
cleanliness +30, happiness -5
캐릭터 목욕 애니메이션 1.2초 재생

놀아주기 (play):
happiness +20, hunger -10, cleanliness -10
캐릭터 놀기 애니메이션 1.2초 재생

치료하기 (treat):
health +30, money -100원
100원 미만 시 치료 불가
캐릭터 치료 애니메이션 1.2초 재생

모든 스탯은 0~100으로 clamp 처리되어 범위를 초과하지 않는다.

[전투 후 스탯 감소 - afterBattle]

전투가 끝날 때마다 캐릭터의 상태가 조금씩 악화된다.
health -1 (고정)
hunger, happiness, cleanliness 중 무작위 1개 -1

이를 통해 전투를 반복하면 캐릭터 관리(육성)가 필수적으로 요구된다.


3.3 훈련 시스템

담당: 이현빈

[훈련 선택 화면 - TrainingScreen]

3개의 미니게임으로 구성된다.
샌드백치기 (PunchingBagScreen) → 공격력 훈련
달리기 (RunningScreen)         → 체력 훈련
반응속도 (ReactionScreen)      → 민첩 훈련

[샌드백치기 - PunchingBagScreen]

총 10회 펀치를 입력해야 훈련이 완료된다.
버튼 클릭마다 퍽! 피드백 텍스트와 300ms 애니메이션이 표시된다.
진행 바([██████░░░░])로 진행 상황을 시각화한다.
10회 완료 시: trainAttack(8) → 공격력 +8
훈련 시 부작용: hunger -5, happiness -5

[달리기 - RunningScreen]

총 10걸음을 입력해야 결승선에 도달한다.
캐릭터 ASCII 아트가 버튼 클릭마다 화면 왼쪽에서 오른쪽 결승선으로 이동한다.
(이동량 = runCount * maxShift / TOTAL_STEPS 으로 부드럽게 이동)
10걸음 완료 시: trainHp(20) → 최대HP +20, 현재HP도 즉시 회복
훈련 시 부작용: hunger -5, happiness -5

[반응속도 - ReactionScreen]

5단계 상태 머신으로 구현된다.
INTRO(1.5초) → WAITING(1~3초 랜덤) → SIGNAL(최대 0.6초) → JUDGED → RESULT

WAITING 중에는 파란색 화면으로 집중 상태를 표시한다.
SIGNAL 발생 시 화면이 노란색으로 바뀌며 "지금!" 버튼을 클릭해야 한다.

반응 시간에 따른 민첩 획득량:
100ms 미만 → 민첩 +6
100~200ms  → 민첩 +5
200~300ms  → 민첩 +4
300~400ms  → 민첩 +3
400~500ms  → 민첩 +2
500ms 이상  → 민첩 +1
0.6초 초과 또는 신호 전 클릭 → 훈련 실패 (획득 없음)

std::chrono::steady_clock 기반 논블로킹 방식으로 구현하여,
대기 중에도 입력을 지속적으로 받을 수 있다.
훈련 시 부작용: hunger -5, happiness -5

UTF-8 바이트 시퀀스를 파싱하고 한글·이모지·CJK 문자를 2칸으로 계산한다.
이를 통해 한글이 포함된 화면에서도 정확한 컬럼 정렬이 보장된다.

================================================================================
4장. 객체지향 설계 원칙 적용
================================================================================

본 프로젝트에서 적용한 C++ OOP 요소를 정리한다.

[추상 클래스와 인터페이스]
Screen 클래스는 render()와 handleInput() 두 개의 순수 가상 함수를 선언하여
모든 화면이 반드시 구현해야 할 계약(contract)을 정의한다.
Screen은 직접 인스턴스화가 불가능하다.

[상속]
8개의 화면 클래스가 Screen을 공개 상속한다.
각 클래스는 화면 고유 동작을 오버라이딩으로 구현한다.

[다형성]
GameEngine의 currentScreen은 unique_ptr<Screen> 타입 하나로 선언된다.
currentScreen->render(player)와 currentScreen->handleInput(...)이 호출될 때,
런타임에 실제 파생 클래스의 메서드가 호출된다 (가상 함수 디스패치).
화면 전환 시 if-else 분기 없이 std::move로 소유권만 이전하면 된다.

[캡슐화]
Character, Monster, BattleScreen 등 모든 클래스의 멤버 변수는 private으로 선언된다.
외부 접근은 public getter/setter를 통해서만 이루어진다.
Character::clampStats()는 private으로 선언되어 내부 유틸리티로만 사용된다.

[정적 멤버]
Renderer의 모든 메서드와 색상 상수는 static으로 선언된다.
인스턴스 생성 없이 Renderer::clearCanvas() 형태로 어디서든 호출 가능하다.
Monster::generateStageMonster(stage)도 static 팩토리 메서드로 구현된다.
Equipment.h, Item.h의 티어 테이블(SWORD_TABLE, ARMOR_TABLE, ITEM_TABLE)은 static const 배열로 선언된다.

[스마트 포인터]
GameEngine의 currentScreen은 unique_ptr<Screen>으로 관리된다.
화면 전환 시 std::move를 통해 소유권이 이전되며, 이전 화면은 자동 해제된다.
메모리 누수 없이 가상 소멸자(virtual ~Screen())와 함께 안전하게 동작한다.

[가상 소멸자]
Screen::~Screen()은 virtual로 선언되어,
기반 클래스 포인터를 통한 삭제 시 파생 클래스 소멸자가 올바르게 호출된다.

[상태 머신 (enum class)]
BattleScreen: BattleState (STAGE_SELECT, ITEM_SELECT, COMBAT_MAIN, BATTLE_WIN, BATTLE_LOSE)
PunchingBagScreen: PBState (IDLE, DONE)
RunningScreen: RNState (IDLE, DONE)
ReactionScreen: RCState (INTRO, WAITING, SIGNAL, JUDGED, RESULT)
EquipmentScreen: EquipState (MAIN, ITEM_SHOP)
enum class를 사용하여 타입 안전한 상태 관리를 구현하였다.

[생성자 멤버 초기화 리스트]
Character, BattleScreen, ReactionScreen 등은 생성자 초기화 리스트를 통해
멤버 변수를 효율적으로 초기화한다.

[RAII]
InputHandler의 생성자에서 raw mode를 활성화하고 소멸자에서 복원하여
예외 상황에서도 터미널 상태가 안전하게 복원됨을 보장한다.


================================================================================
5장. 기술적 도전과 해결 과정
================================================================================

[문제 1: 키 입력을 즉시 받는 방법]

문제: 터미널의 기본 동작은 Enter 입력 후 전달되는 정규 모드(canonical mode)여서,
실시간 반응이 필요한 게임에 사용할 수 없었다.

해결: termios를 사용하여 터미널을 즉시 전달 모드(raw mode)로 변경하였다.
키를 누르는 순간 바로 읽도록 구성하고,
게임이 끝나면 원래 터미널 설정으로 복원하여 게임 종료 후에도 터미널이 정상 동작하도록 처리하였다.
Ctrl+C 등 비정상 종료 시에도 복원되도록 시그널 핸들러를 정적 인스턴스로 등록하였다.


[문제 2: 마우스 클릭 위치 파악]

문제: 터미널에서 마우스 클릭 정보는 ESC 코드로 시작하는 암호 같은 바이트 시퀀스로 전달된다.
어디를 클릭했는지 파악할 수 없었다.

해결: xterm 마우스 프로토콜 스펙을 분석하여 단계별로 파싱하는 파서를 직접 구현하였다.
파싱 결과를 InputEvent 구조체(type, button, x, y)로 정규화하여
모든 화면에서 동일한 방식으로 클릭 위치를 사용한다.


[문제 3: 한글·이모지가 섞이면 화면 정렬이 깨지는 문제]

문제: 한글이나 이모지는 터미널에서 두 칸을 차지하지만, C++ string::size()는 바이트 수만 반환한다.
그래서 화면 정렬 계산 시 실제 표시 너비와 다른 값이 나와 화면이 틀어졌다.

해결: getDisplayWidth() 함수를 직접 구현하였다.
UTF-8 바이트 시퀀스를 직접 파싱하여 한글·이모지·CJK 문자는 2칸, ASCII는 1칸으로 계산한다.
모든 패딩·중앙정렬 함수가 이 함수를 사용하여 정확한 터미널 정렬을 보장한다.


[문제 4: 미니게임 타이머와 입력을 동시에 처리하기]

문제: 반응속도·샌드백 미니게임은 "N초 뒤에 반응하세요" 같은 대기 시간이 필요한데,
기존 sleep() 방식으로 대기하면 그동안 입력을 전혀 받지 못하였다.

해결: std::chrono::steady_clock으로 현재 시각을 기록해두고,
매 프레임(handleInput 호출)마다 경과 시간을 체크하는 논블로킹 방식으로 변경하였다.
덕분에 대기 중에도 입력을 계속 받을 수 있고,
게임 상태 전환은 상태 머신(enum + enterState 함수)으로 통일하였다.


================================================================================
6장. 테스트 및 검증
================================================================================

별도의 자동화 테스트 프레임워크는 사용하지 않았으며,
빌드 후 직접 실행하는 수동 테스트 방식을 채택하였다.

테스트 항목 및 결과:

방법 - 5스테이지 전체 가위바위보 전투 진행
결과 - 정상

훈련 미니게임 3종:
방법 - 각 게임 플로우 후 스탯 획득 확인
결과 - 정상

게임 오버 조건:
방법 - 스탯 극한까지 낮춰 종료 트리거
결과 - 정상

결과 - 정상

장비 강화:
방법 - 검/갑옷 강화 성공·실패 케이스 확인
결과 - 정상

아이템 구매 및 전투 사용:

[OOP 학습 성과]

추상 클래스(Screen)를 중심으로 8개 구체 화면 클래스를 설계·구현하여
코드 중복 없이 다형성으로 게임 루프를 운영하는 구조를 완성하였다.

termios, ANSI Escape Code, xterm 마우스 프로토콜 등
OS·터미널 수준의 저수준 시스템 프로그래밍 기술을 직접 구현하였다.

std::chrono 기반 논블로킹 상태 머신으로 3종의 반응속도 미니게임을 구현하였다.

UTF-8 디코딩과 유니코드 너비 판별로 한글·이모지가 포함된 터미널 UI를
정확히 정렬하는 기능을 구현하였다.

Git을 통한 버전 관리 및 코드 리뷰 경험을 습득하였다.


[기대효과]

대중성과 게임성의 조화:
친숙한 '다마고치'의 대중성에 RPG의 전략을 더하여,
폭넓은 사용자 층에게 익숙하면서도 새로운 몰입감을 제공하는
독창적인 게임 콘텐츠를 제시한다.

로직 설계 가시화:
그래픽에 가려지기 쉬운 복잡한 로직을 터미널 환경 특유의
직관적인 텍스트 출력으로 시각화하여,
로직 구현 및 프로그램 구조를 명확히 입증한다.

확장된 게임 메커니즘 제시:
기존 다마고치 유저들에게 단순한 '생존과 돌봄'을 넘어
'전투와 모험'이라는 새로운 목표를 제시함으로써,
익숙한 캐릭터로 즐기는 차별화된 엔터테인먼트 경험을 제공한다.

객체지향 학습 및 모범사례:
복잡한 상태 관리와 객체지향 설계의 정석을 담아,
개발 학습자를 위한 객체지향 프로그래밍 교육용 레퍼런스나
로직 설계의 모범 사례로 활용 가능하다.

저사양 환경 적용:
터미널만 있으면 실행 가능하므로 라즈베리파이, 서버 환경 등
GUI가 없는 환경에서도 동작한다.

교육용 게임 템플릿:
유사한 TUI 기반 게임 개발의 참고 아키텍처로 활용 가능하다.
